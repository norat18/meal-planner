# Short List

Short List (formerly Macro Prep Planner; the repo is still `meal-planner`): a single-file web app (`public/index.html`) hosted on Firebase at https://short-list-meals.web.app (project `macro-prep-planner-nt`, display name "Short List"; the old https://macro-prep-planner-nt.web.app redirects there, owned by ntan.nora@gmail.com, Blaze plan with a $5 budget alert). Each person signs in with Google and gets a private library: their data lives in Firestore under `users/{uid}/` (`recipes/{id}`, `app/settings`, `app/plan`), and `firestore.rules` lets only that user read or write it. Recipe import runs in a Cloud Function (`functions/index.js`, `importRecipe`) that calls the Claude API; the key is the Firebase secret `ANTHROPIC_API_KEY` and must never appear in the HTML or the repo. The old Claude artifact (https://claude.ai/artifact/5A7gHTp8iMiAsQLHve2ewE) is retired; don't republish it.

Product requirements: the Meal Planner PRD (https://claude.ai/artifact/9BXoW42Dy7DLeDKsfsdaY3). Its acceptance criteria are the spec.

## Deploying

- Firebase CLI: `npx firebase-tools@13.29.1 <command>` (no global install on this Mac).
- `firebase deploy --only hosting` for HTML changes (two sites: `short-list-meals` serves the app, `macro-prep-planner-nt` only redirects to it); `--only firestore:rules` for rules; `--only functions` for the import function.
- On localhost the app uses browser storage instead of Firebase, so testing at http://localhost:8765/public/index.html never touches real accounts (add `?firebase` to the URL to test against Firebase).
- The web config in `FIREBASE_CONFIG` is public by design; access is enforced by `firestore.rules` and sign-in.
- Never commit recipe data (`recipes.json`, `*backup*.json`): the recipes are copyrighted (meal kits, a coach) and private.

## How the week is planned

- **Rules, in priority order (PRD):** macro targets when set (each day within its tolerance; ±10% by default, Nora uses ±3%), then variety (no recipe cooked twice in the week, at least 2 cuisines unless "Minimize groceries" is on), then the fewest unique ingredients. Items marked "I already have this" (`settings.have`) don't count. Snacks aren't cooked, so they may repeat up to `maxRepeat` days but not reuse a cooked meal. Targets are optional (`useTargets`); without them everyone eats one serving.
- **Fiber goal:** `settings.fiber` is a daily minimum in grams (0 = off), independent of `useTargets` but ranked with the macro targets when planning; a day is short when it is more than 0.5 g under. Recipes carry `fib` (grams per serving) and `fibEstimated`; all 285 existing recipes got Claude estimates on Oct 16, 2026, and imports extract or estimate fiber.
- **Household size** (`household`) scales recipe amounts and the grocery list; macros stay per person.
- **Purchase units:** the grocery list converts produce and eggs sold by the piece into what you buy (400 g onion -> 3 onions), using the `PURCHASE` table of average piece weights and grams per cup; it rounds up, ignoring a remainder under 0.15, and shows the recipe amounts underneath. Prepared forms (powder, paste, canned, frozen...) and items sold by weight stay as they are.
- **Easy units:** the recipe sheet shows each amount in the easiest kitchen unit (`easyAmount`): pieces for produce, eggs and meat that come as pieces ("1½ onions", "½ curry roux"), cups/tbsp/tsp for flour, grains, cooked rice, dairy and liquids, oz/lb for ground meat and shrimp, cans for canned goods, with the source grams in small print. Ingredients keep their source `qty`/`unit` (grams feed the grocery list) plus `easy: {qty, unit, one, many}`, the same whole-recipe amount (unit "" counts pieces named one/many). All 766 metric amounts got Claude estimates on Oct 16, 2026; imports return `easy` too, and the editor keeps it (scaled) while the row's item and unit don't change. Without `easy`, ml shows as spoons/cups and produce in grams as pieces via `PURCHASE`.
- **15-recipe minimum** before the first plan (`MIN_RECIPES`).
- **Leftovers:** each dinner is cooked once and eaten again as the next day's lunch (Sunday's dinner is Monday's lunch). Setting `leftovers` turns this on and it is on by default. Picking, pinning or clearing either slot changes both. Portions may differ between the two meals so each day still hits its targets.
- **Big batches:** a dinner can make 2 (default), 3 or 4 meals; extra meals fill the next slots in a row (4 = that dinner, next lunch, next dinner, the lunch after), via `plan.batch[day] = { k, auto }`. Hand-picked batches (`auto: false`) are kept; the planner places `settings.bigBatches` more of size `batchSize` when planning a full week, at least 2 days apart. A lunch left over after an odd batch is cooked fresh.
- **Breakfast rotation:** setting `bfRotation`, also on by default, repeats breakfasts in blocks; `bfMode` picks the blocks: `"three"` (Mon–Tue, Wed–Thu, Fri–Sun) or `"two"` (Mon–Thu, Fri–Sun). The last block is always Fri–Sun. Fri–Sun breakfasts must be car-friendly: recipes with `portable: true`, which covers handhelds like burritos, wraps, muffins, bagel or English-muffin sandwiches, plus drinkable smoothies and shakes. Tag new car-friendly breakfasts with `portable: true`.
- Recipe ids by source: `st-` Strong, `hp-` Coach Greg, `my-` Homemade, `hf-` HelloFresh, `gc-` Green Chef, `ba-` Blue Apron, plus the monthly pack prefixes (`bk-`, `jan-`, `oct-` and so on).

## Logging meals in MyFitnessPal

MyFitnessPal has no public API, so the app offers two manual paths and Claude can do a third on request:

- **Barcode:** only recipes with an `mfp` field (`{format: "UPC" | "UPCE", code}`) show a barcode. These are the codes printed in the Coach Greg packs, decoded from the PDFs' barcode images, and they scan because the coach's foods are already in MyFitnessPal's database. Don't generate barcodes for other recipes: Nora's MyFitnessPal app gives no way to link a new barcode to a food, and the website's create-food form has no barcode field, so generated codes always scan as "no match" (tried and removed).
- **Search:** recipes without a barcode are created as public foods on myfitnesspal.com (My Foods), with brand `Homemade` (`my-` ids), `Strong` (`st-`), `Coach Greg` (`hp-`), `HelloFresh` (`hf-`), `Green Chef` (`gc-`) or `Blue Apron` (`ba-`), description = recipe name, 1 serving, servings per container = recipe servings, and calories, fat, carbs and protein per serving. Current foods are named "Strong <recipe name>" under the brand (created Oct 16, 2026 with fiber, and for non-Coach-Greg recipes the full panel: saturated/poly/mono/trans fat, cholesterol, sodium, potassium, sugar, vitamins A and C, calcium, iron, estimated by Claude). Coach Greg's barcode-less recipes were recreated the same day as "Strong Full <recipe name>" with the full panel too, superseding their "Strong <name>" copies. The recipe view tells Nora to search "<brand> Strong <name>", or "Coach Greg Strong Full <name>" (`mfpSearch`/`mfpPrefix`). MyFitnessPal refuses edits to public foods ("Public foods cannot be updated"), so a change means creating a new food; the older copies without "Strong" are superseded and Nora deletes them herself in the MyFitnessPal app (deleting data is hers to do). Create foods by POSTing the same body the website's create form sends to /api/services/foods from a signed-in myfitnesspal.com tab, skipping names that already exist. A recipe changed from its source (e.g. a coach recipe with a swapped ingredient) gets its own food: set `mfpBrand` (and `mfpName` if the food's name differs) on the recipe and remove its `mfp` barcode, since the barcode would log the original numbers. Example: `jan-chicken-katsu`, renamed Tonkatsu Curry, is "Homemade Tonkatsu Curry". When a recipe is added or its macros change, update the matching MyFitnessPal food too.
- **Quick Add copy:** every recipe view and day card can copy calories, carbs, fat and protein (MyFitnessPal's Quick Add field order) at the planned portion.
- **Claude logs it in Chrome:** when Nora asks (for example "log today's lunch"), read the plan and recipes (Nora can export them from Targets → Download a backup, or share her screen), compute each meal's numbers at its portion (`recipe macros × x`), then use Claude in Chrome on myfitnesspal.com, signed in as Nora, to add each meal to the right Diary section with Quick Add. Show the entries and get her OK before saving each one. Only do this when she asks; never log meals on your own.

## Git workflow

- After finishing each change the user asks for, commit it and push to GitHub (`origin`, private repo `norat18/meal-planner`, branch `main`) without asking first.
- Write a clear commit message: a short summary line saying what changed, then a body explaining why when it isn't obvious.
- One commit per requested change. Don't bundle unrelated changes.
- Before committing, check the staged diff for API keys, tokens, passwords or other secrets, and never commit `.env` files.
- If a change only touched someone's data in Firestore (recipes, targets or plans), there's nothing to commit. Say so instead of making an empty commit.
- If the HTML, rules or function changed, also deploy to Firebase so the live app matches the repo.
- `gh` lives at `/opt/homebrew/bin/gh`, which may not be on PATH.
